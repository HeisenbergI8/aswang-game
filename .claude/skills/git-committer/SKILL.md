# Git Committer

**Only commit when the user asks.** Never commit as a side effect of finishing a task.

Read `git log -5` before writing anything and match what you find.

## The one rule

**The body explains WHY. The diff already shows what and how.**

Test every line you are about to write against that. If the reader could learn it by reading the diff,
cut it.

## Anatomy

```
type(scope): imperative summary, lower case, no period

The problem this solves, stated concretely — what was broken, what it cost,
or what changed that forced this.

Any decision a reader would otherwise question: a non-obvious approach, a
constraint you were working around, something deliberately left out.
```

**Subject.** Aim for **50 characters**, hard limit 72. Imperative — "add", not "added". Types: `feat`,
`fix`, `docs`, `refactor`, `chore`, `test`, `balance`. Scope is the system, matching the module layout:
`round`, `roles`, `monster`, `tasks`, `salt`, `ghost`, `trial`, `progression`, `monetization`,
`analytics`, `anticheat`, `ui`, `harness`, `config`.

`balance` is a type rather than a scope on purpose. A commit that only moves numbers in `Config.luau` is
a distinct kind of change, it happens constantly during M12, and being able to `git log --grep balance`
is how you reconstruct what a playtest session was actually testing.

**Body.** Wrapped at **72**. Blank line after the subject, always. Two or three short paragraphs. If the
body exceeds ~15 lines, you are describing the diff or committing two things.

## What does NOT belong

Each of these is either stale on arrival, already visible, or about you rather than the change:

- **Verification output.** `13/13 invariants`, `exit 0`, `analyze clean`. True for one commit and
  misleading thereafter.
- **A summary of the diff.** "Adds X to file A, Y to file B."
- **Implementation mechanics.** How a mapper coerces a value, which helper you reused.
- **Process commentary.** What you verified, how many attempts it took, what an agent found.
- **Section headers and tables.** A commit body is prose, not a document.
- **Tool attribution.** No `Co-Authored-By`, no `Generated with`, no session link. This is enforced in
  `.claude/settings.json` via `attribution`, so it holds even if these instructions are not read.

## What DOES belong

- The problem, in one or two sentences.
- A decision that would otherwise look wrong — *"Roles are stored in a server-side table keyed by UserId
  rather than an attribute, because attributes replicate to every client."*
- Something deliberately excluded, so nobody thinks it was forgotten.
- **A balance change's intent and its evidence.** `balance(monster): raise kill cooldown to 35s` should
  say which playtest produced it and what it is meant to fix. Six months later, the number is in `Config`
  and the reason is only here.

If none of these apply, the subject line alone is a complete commit message. That is a perfectly good
outcome.

## Verify before writing, but do not narrate it

```bash
npm run verify
```

Run it. `guard-commit.mjs` blocks a commit on a red tree anyway, but finding out before you have written
the message is cheaper.

Never claim a gate you did not run — the `Stop` claim gate checks assertions about verification against a
ledger of what actually executed.

## What must never be committed

`guard-commit.mjs` refuses these, and the reasons are worth knowing rather than being surprised by:

| Never | Why |
| --- | --- |
| `*.rbxl`, `*.rbxlx` | The MAP. Binary, merge-hostile, and backed up by Roblox cloud version history — not Git |
| `sourcemap.json` | Generated by `rojo sourcemap` |
| `.luau-defs/` | ~1MB of fetched Roblox API definitions; a build input |
| `build/` | Build output |
| `.claude/.*` | Harness runtime state |

**`.claude/` itself IS tracked** — agents, skills, scripts and lessons are the project's process, and an
untracked harness has no history and cannot be reviewed in a diff. Commit changes to it like any other
code, scoped `harness`.

**`analyze-baseline.json` is tracked deliberately.** It is the single input that decides whether the gate
can be satisfied at all, so a commit that widens it needs a sentence saying why in the body. That is the
whole reason it lives at the repo root rather than under gitignored `.claude/`.

## Scope

One commit is one coherent change. When you find yourself writing "and also" in the body, it is two
commits.

If a prerequisite refactor was needed, **commit it separately, first**. Bundling it and explaining the
bundle in the body is what produces long commits — the explanation is only necessary because the commit
does two things.

## Procedure

1. `git status` and `git diff` — read everything you are about to stage. Never `git add -A` without
   looking; this repo has untracked artifacts that must not be committed.
2. Confirm the branch. If you are on `main`, branch first and tell the user.
3. Run `npm run verify`.
4. Stage deliberately — name the paths.
5. Write the message to a heredoc so the body formatting survives, then `git commit -F`.
6. Report the result and stop. **Do not push unless the user asks.**
